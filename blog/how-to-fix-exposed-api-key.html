Exposed API Key in Your Code? Here Is How to Fix It

6 min read · Updated 2026

You found a live API key sitting in your source, or realized you pushed one to GitHub. First: do not panic, but do move quickly — exposed keys get scraped by bots within minutes. Here is exactly what to do, in order.

Step 1: Rotate the key immediately

Assume the key is already compromised. Go to the provider's dashboard (Stripe, OpenAI, AWS, etc.), revoke or roll the exposed key, and generate a new one. Rotating first means that even if a bot already grabbed it, the old key is dead. Everything else is cleanup.

Step 2: Move the new key to an environment variable

Never put the replacement back into the code. Read it from the environment instead:

Safe// Node
const key = process.env.STRIPE_SECRET_KEY;

// PHP
$key = getenv('STRIPE_SECRET_KEY');

Set the value in your host's environment settings (or a local .env file that is not committed), and add .env to .gitignore.

Step 3: Remove the key from Git history

Deleting the key in a new commit is not enough — it still lives in history. For a recent commit, the fastest route is to scrub it:

Clean history# back up first, then:
git filter-repo --replace-text <(echo "OLD_KEY==>REMOVED")
# or use the BFG Repo-Cleaner for larger histories
git push --force

If the repo is small and new, it can be simpler to delete it and push a fresh one with the key already gone.

Step 4: Check for other exposed secrets

If one key leaked, others often did too. Scan the whole project for keys, tokens, and connection strings before you move on.

Step 5: Stop it happening again

  • Keep all secrets in environment variables, never in code.
  • Add .env and key files to .gitignore from day one.
  • Turn on push protection / secret scanning on your Git host.
  • Scan before every deploy.

Frequently asked questions

What should I do if I exposed an API key?

Rotate the key immediately in the provider dashboard, move the new key to an environment variable, remove the old key from Git history, scan for other leaked secrets, and add .env to .gitignore to prevent it recurring.

Is it enough to just delete the key from my code?

No. A key committed to Git stays in the repository history even after you delete it in a new commit. You must scrub it from history or recreate the repo, and you should rotate the key regardless.

How do bots find exposed keys so fast?

Automated scanners watch public repositories and the web continuously and can grab a newly committed key within minutes, which is why rotating the key is the first and most important step.
