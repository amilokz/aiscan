Secure a Next.js App: Pre-Deploy Checklist

7 min read · Updated 2026

Next.js blurs the line between server and client, which is where most of its security mistakes live. Run through this checklist before you deploy — it covers the issues that actually get Next.js apps breached.

1. Keep secrets off the client

Only NEXT_PUBLIC_ variables are safe to expose — and they are compiled into the browser bundle, so never put keys there. Read real secrets in server components, route handlers or server actions only.

2. Authenticate every API route and server action

A route handler or server action that mutates data must verify the session first. Do not assume the UI hides it — the endpoint is directly reachable.

Safeexport async function POST(req) {
  const session = await auth();
  if (!session) return new Response("Unauthorized", { status: 401 });
}

3. Protect routes in middleware

Use middleware.ts to guard whole sections (like /admin) rather than relying on client-side redirects, which are trivial to bypass.

4. Validate input on the server

Validate the shape and type of request bodies (with Zod or similar) before they touch your database or an external API.

5. Parameterize database queries

Whether you use Prisma, Drizzle or raw SQL, never concatenate input — see preventing SQL injection.

6. Set security headers

Add CSP, HSTS and the rest in next.config.js headers or your reverse proxy — our headers generator gives you a starting set.

Frequently asked questions

How do I keep API keys secret in Next.js?

Read them only in server code (server components, route handlers, server actions) from non-public environment variables. Anything prefixed NEXT_PUBLIC_ is bundled into the browser and visible to all users.

Where should I put authentication in a Next.js app?

Check the session inside every mutating route handler and server action, and guard whole route groups with middleware.ts. Do not rely on client-side redirects, which users can bypass.
